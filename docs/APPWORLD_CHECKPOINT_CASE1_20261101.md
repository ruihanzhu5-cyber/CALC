## 轨迹确认了什么

检查点确实进入了模型的正常决策：初始化、异常、发现歌单、计划变化均有记录，模型明确选择继续。
它没有提出分派，merge/fold 因而没有执行。模型把工作组织成当前 loop 内逐首查询，
没有采用前轮按点赞数排序缩小范围的查询策略。

实际得到的歌单列表只有默认第一页5个歌单，统计了38首不同歌曲并逐首查询。
这不是完整读取全部8个歌单，因此不能接受它“已经检查所有歌单”的说法。
模型最终识别到同一歌曲标题，但提交到 supervisor.complete_task.answer 的字段含整句说明，
而非用户所问的标题值，官方答案匹配失败；无意外状态修改断言通过。
官方结果保留为失败，不因歌曲名称正确而改成成功。

## 新实现暴露的工程问题

12次进度协议错误包括：

- 8次模型手填 observed_version 与执行状态不一致。
- 3次未在要求的检查点报告进度。
- 1次填写了不存在、重复或已评估的 checkpoint ID。

5个集合事件中，只有1个来自主歌单结果；另外4个来自单曲详情内的 artists 附属列表。
另外有2个普通工具错误事件、2个计划变化事件和1个初始任务事件。
触发器应提供有价值的评估机会，这些附属对象与容易本地修复的错误不应都变成强制评估。

## 实跑后已经修改，但未再次调用付费模型

1. 报告的请求版本和检查点 ID 由运行时快照并绑定，模型只填写进度、证据和决策等语义内容。
   并发后状态已改变仍明确拒绝旧请求；没有取消并发新鲜度检查。
2. 集合检测限定主结果列表及 results/items/records/data 封装，忽略单条记录的附属列表。
   普通工具错误只留在本地，终态失败/明确阻塞仍通知相关父节点。
3. AppWorld 公开工具使用提示增加分页检查及精确提交用户所问值的要求，解释放在最终消息。
   不读取评分结果指导运行，不注入具体答案，不改变官方评分或程序自动清洗答案。

离线重放本次工具观察：原5个集合事件降为1个主结果集合，保留歌单发现事件，排除4个附属集合；
模型需要的报告字段不再含 observed_version 或 checkpoint_ids。审计为零模型请求，
记录在 `postrun_protocol_audit.json`，不是一次新的 benchmark 结果。
